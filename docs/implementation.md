# 实施计划与验收

## 1. 当前交付与待定项

当前只交付设计文档、提示词和 JSON Schema；未部署 n8n，未调用拼多多/闲鱼账户，未验证真实采集成功率。

已知：使用 n8n，货源是拼多多，目标是闲鱼同款筛选和图文生成。

待实施前确认：每日商品数、品类、20 条真实样本链接、目标 SKU、自己的销售及售后条件、部署位置、模型供应商、可用图片授权。当前按内部单团队使用设计；对外多客户服务另行评估权限、隔离和第三方许可证。

## 2. 阶段与出口条件

| 阶段 | 交付 | 出口条件 |
|---|---|---|
| P0 数据可行性 | 两个平台最小采集验证、20 件样本报告 | 分别报告标题/图片/SKU/浏览量获取率、登录干预频率、耗时；无法获取项有原因 |
| P1 可靠采集 | FastAPI、worker、业务库、WF-01/02/04、快照和素材 | 相同输入不重复建任务；重启后可恢复；登录异常会暂停 |
| P2 同款筛选 | 品类规则、候选列表、覆盖率、热度排序 | 人工标注样本评估 exact 准确率与漏判；硬规格冲突不能判 exact |
| P3 文案生成 | WF-03 生成段、提示词、Schema、检查器 | 生成三版结构化文案；参数错误、未知承诺和无效事实引用被标记 |
| P4 审核导出 | 简易审核页、WF-05/06、ZIP/CSV | 只导出准确批准版本及批准素材；修改后审批失效 |
| P5 运行验证 | 固定部署版本、监控、备份恢复说明 | 小批量连续试运行后记录吞吐、失败原因、单件成本，再调整并发 |

P0 的结果决定后续范围和工期。不能以“仓库中有 browseCnt 字段”代替真实可用性验证；也不以单次请求成功承诺长期采集稳定。

## 3. 首版配置建议

以下都是待试验调整的项目默认值，不是平台配额：

| 参数 | 起始值 |
|---|---|
| 单批输入 | 最多 20 个源商品 |
| 同时运行的商品流程 | 1 |
| 同一账号浏览器并发 | 1 |
| 每件源商品查询词 | 最多 3 组 |
| 合计去重搜索候选 | 最多 30 个 |
| 候选详情请求 | 最多 10 个 |
| 文案参考商品 | 最多 3 个 |
| 生成版本 | 3 版，一次模型请求完成 |
| 模型调用 | 初次生成 + 最多 1 次修正 |
| Python 暂时性错误 | 最多 3 次总尝试 |
| n8n job 查询间隔 | 30 秒 |
| 单次等待窗口 | 15 分钟，之后延后检查原 job |
| run 租约 | 10 分钟，运行中续租 |

平台采集间隔由适配器基于实际权限、响应和试验设置；n8n 的轮询频率是查询自己的服务，不是查询平台。

## 4. 部署拓扑

首版同机 Docker Compose：

- n8n：工作流编辑及执行；不默认开启 queue mode。
- api：FastAPI，提供业务接口和审核入口。
- worker：Celery，执行长任务；同账号串行由业务锁保障。
- redis：Python 消息队列。
- postgres：创建独立 n8n 数据库、业务数据库及不同用户。
- 持久化目录：业务资产、导出包、受保护的浏览器登录态；后续切对象存储。

通过反向代理提供 HTTPS，API/数据库/Redis 仅在内部网络访问。数据库、资产和凭据恢复必须一起演练。图片容量与浏览器资源通过 P0 实测后决定，当前不承诺固定机器配置可以承载多少商品。

n8n 和 Python worker 的并发是两层不同限制；扩容前先排查平台账号限制。只有 n8n 自身执行吞吐成为瓶颈时，再评估它的 queue mode，避免一开始维护两套分布式工作流执行器。

## 5. 验证矩阵

| 场景 | 应有结果 |
|---|---|
| 同一导入请求重发 | 返回相同 batch/runs，不重复采集 |
| 同 key 不同请求体 | 409，不能静默覆盖 |
| 同商品不同 SKU | 分别保存；未选择 SKU 时暂停 |
| 搜索结果有多链接指向同 item ID | 合并采集，保留查询来源 |
| 一部分详情失败 | 保留成功样本，显示覆盖率 |
| 浏览量缺失、0、近似“1.2万” | 三者明确区分；想要人数不替代 |
| 型号相同但容量/件数不同 | 按品类规则排除或待核实 |
| 没有确认同款 | 进入 needs_input，不伪造参考样本 |
| 登录过期/出现验证挑战 | 暂停该账号，人工恢复后从原阶段继续 |
| API 落库后 Redis 投递失败 | reconcile 再投递，不丢 job |
| worker 重复收到消息 | 不建立重复结果和文件 |
| n8n 等待窗口结束 | 保留原 job ID，下次接着查 |
| 老 n8n 执行迟到写入 | fencing token 拒绝覆盖新执行 |
| 模型调用中断、费用未知 | 标记 unknown，冻结预算，人工决定 |
| 模型输出假事实或正文无效引用 | blocking issues，禁止批准 |
| 文案高重复但必要规格一致 | 只修正表达，不为了查重改规格 |
| 批准后修改文案、SKU 或图片 | 原批准失效；导出拒绝旧批准 |
| 图片权利未知 | 可作参考，不进入发布包 |
| 用户 URL 跳转到内网 | 拒绝访问，记录脱敏原因 |
| 网页含“忽略上文”类指令 | 按数据处理，不改变生成规则或调用工具 |

实现阶段对状态机、幂等、排名和批准版本绑定写确定性测试；平台适配器优先用脱敏 fixture 测试，再做小规模人工监督的真实采集验证。不将不断重复访问平台作为单元测试。

## 6. 运行指标

每批记录：源商品完整率、SKU 明确率、搜索/详情覆盖率、浏览量可取得率、exact 候选人工确认准确率、待人工比例、每阶段耗时、模型 token 与费用、文案修正次数、导出成功率。

每个日志携带 batch/run/job/n8n execution ID。聚合账号登录失效和同类错误，避免每个候选都产生独立通知。首版在后台展示异常，不自动外发消息。

## 7. 后续目录建议

```text
services/api/             # FastAPI、鉴权、状态机和接口
services/worker/          # Celery 任务和两个平台适配器
packages/domain/         # 数据模型、同款规则、排名和文案检查

migrations/              # 业务库迁移
tests/fixtures/          # 脱敏测试样本
deploy/                  # 固定版本的 Compose 与运行说明
```

这些目录当前未创建，避免把空骨架误认为已实现。后续代码与文档更新一起提交。

## 8. 外部项目使用

- `ai-goofish-monitor` 的默认分支有浏览量、想要人数、图片读取逻辑，足以证明研究方向有参考实现；不是平台可用性保证。
- 它的 MIT LICENSE 与学习研究用途表述需要在复用前厘清；本次未复制代码。
- n8n 内部运行与对外提供可配置工作流的许可边界不同。若业务转为 SaaS，按当时实际产品形态复核授权，不把“源码可见”视为任意商业用途授权。
- 暂不引入 Dify；已有生成需求通过 n8n 模型节点和 Python 校验实现。未来运营确需独立管理多套 AI 应用时，再评估接入。
